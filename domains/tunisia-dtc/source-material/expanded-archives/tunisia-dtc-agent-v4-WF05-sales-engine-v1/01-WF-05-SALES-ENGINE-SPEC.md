# WF-05 Sales Engine — Production Specification v4

## 1. Role

WF-05 is the sales business-logic workflow between WF-04 Intent Router and the downstream reasoning/action pipeline.

It determines the **allowed sales path**, required facts, next business step, and sales-stage transition.

It is not the LLM and is not the authorization boundary.

## 2. Inputs

Minimum trusted input:

```json
{
  "conversation_id": "conv_123",
  "customer_id": "cust_123",
  "channel": "facebook_messenger",
  "language": "tn",
  "script": "latin",
  "intent": "product_discovery",
  "sales_stage": "DISCOVERY",
  "identity_level": 1,
  "identity_status": "CHANNEL_LINKED",
  "conversation_owner": "AI",
  "automation_mode": "FULL",
  "selected_products": [],
  "cart_id": null,
  "order_scope_ids": [],
  "risk_flags": [],
  "turn_count": 4
}
```

Customer text and LLM suggestions remain untrusted.

## 3. Sales state machine

Primary states:

```text
NEW
→ BROWSING
→ DISCOVERY
→ PRODUCT_INTEREST
→ CONSIDERING
→ PRODUCT_SELECTED
→ CART_BUILDING
→ CHECKOUT_READY
→ PURCHASED
→ POST_PURCHASE
```

Supporting states:

```text
OBJECTION_HANDLING
WAITING_FOR_CUSTOMER
HUMAN_ESCALATION
CLOSED
```

WF-05 may only perform transitions that are explicitly allowlisted.

## 4. State-transition rules

| Current | Trigger | Next |
|---|---|---|
| NEW | valid product-related inquiry | BROWSING |
| BROWSING | needs discovery | DISCOVERY |
| DISCOVERY | suitable product candidates exist | PRODUCT_INTEREST |
| PRODUCT_INTEREST | customer evaluates options | CONSIDERING |
| CONSIDERING | customer chooses product/variant | PRODUCT_SELECTED |
| PRODUCT_SELECTED | customer requests cart action | CART_BUILDING |
| CART_BUILDING | cart is complete and customer asks checkout | CHECKOUT_READY |
| CHECKOUT_READY | verified purchase/order event | PURCHASED |
| PURCHASED | after-sales sales context | POST_PURCHASE |

`OBJECTION_HANDLING`, `WAITING_FOR_CUSTOMER`, `HUMAN_ESCALATION`, and `CLOSED` are controlled side states.

A customer saying “zidhali taille 42 lel panier” must be interpreted through the routed cart intent, not downgraded to generic product discovery.

## 5. Discovery

Collect only information useful for matching:

- need/use case
- budget when relevant
- preferred variant
- constraints
- quantity
- delivery considerations

Do not interrogate unnecessarily.

WF-05 should prefer progressive discovery:
1. identify immediate need
2. retrieve only necessary product facts
3. ask the smallest missing question
4. move toward a concrete next step

## 6. Product recommendation

Recommendations must be explainable from verified product attributes.

Allowed:
- fit with stated need
- factual differences
- tradeoffs
- compatibility based on verified data

Forbidden:
- invented superiority
- fabricated reviews
- invented customer counts
- unsupported quality claims
- competitor claims without an approved source
- fabricated scarcity or urgency

## 7. Pricing

WF-05 may request price information but never becomes the price authority.

Current price must come from the authoritative commerce/product service.

Never derive a discount from:
- prior conversation
- stale KB content
- another product
- another customer
- a guessed percentage

## 8. Promotions

Promotion intent is delegated to WF-13.

A promotion may be presented/applied only when its validation result is authoritative for the current context.

WF-05 must treat:
- eligibility
- expiry
- minimum subtotal
- product/category restrictions
- usage limits
- stacking
as promotion-service facts.

## 9. Cart

WF-05 identifies the sales step; WF-12 performs the cart operation after WF-10 authorization.

Supported cart intents:

```text
cart_view
cart_add
cart_remove
cart_update
cart_clear
```

For an add/update:
- valid product/SKU/variant
- quantity
- current availability
- authorized session/customer context
- idempotency
- successful post-execution response

## 10. Checkout

WF-05 may transition to `CHECKOUT_READY` only when the business conditions are met.

Before a checkout action:
- current cart must be re-read
- price must be fresh
- inventory must be fresh
- promotion must be fresh where applicable
- checkout must be generated by WF-14/WF-20

Never construct a checkout URL in WF-05 or in the LLM.

## 11. Human ownership

If WF-03 says:

```text
conversation_owner = HUMAN
```

or

```text
automation_mode = PAUSED
```

WF-05 must not autonomously advance consequential sales actions that conflict with the human case.

If:

```text
automation_mode = SAFE_ONLY
```

WF-05 may support safe, non-conflicting informational handling, but consequential actions still require the normal WF-10 path and must respect the active human case.

## 12. Turn and repetition limits

WF-05 consumes trusted turn-count/risk controls from WF-03.

If configured automated-turn threshold is reached:
- stop repetitive selling
- offer human support or close appropriately
- do not keep generating sales loops

Detect:
- same recommendation repeated
- same objection loop
- same failed action
- repeated checkout failure

## 13. Output

WF-05 produces a deterministic sales-plan envelope:

```json
{
  "sales_stage": "PRODUCT_SELECTED",
  "next_step": "CART_ADD",
  "required_facts": ["current_inventory", "current_variant"],
  "allowed_intents": ["cart_add"],
  "action_required": true,
  "human_ownership_block": false,
  "reason_code": "CUSTOMER_SELECTED_VARIANT"
}
```

This output is advisory to downstream authorization; it never sets `execution_allowed`.

## 14. Failure behavior

Fail closed for:
- invalid state
- identity conflict
- human ownership conflict
- missing required context
- stale/unknown commerce state
- repeated automation limit
- unsupported sales transition

Return machine-readable reason codes.

## 15. Analytics

WF-05 can emit:
- `product_viewed`
- `recommendation_made`
- `objection_handled`
- `product_selected`
- `cart_item_added`
- `checkout_started`
- `purchase_completed`

Do not include unnecessary PII or secrets.
