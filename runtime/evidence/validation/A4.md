## The two things that usually break Linux

| Check | Result |
|---|---|
| Shell scripts mode `100755` in git | 177 of 177 |
| Committed files with CRLF | 0, checked across every tracked `.sh` |
| `.gitattributes` | **absent** |

CRLF is clean despite this Windows machine having `core.autocrlf=true`, because that setting converts on checkout and converts back on commit. The blobs are LF. Nothing enforces this, though — see follow-up 1.

## Defect 1: a script was committed non-executable

`scripts/docs/validate-public-docs.sh`, committed minutes earlier as the A3 fix, went in as mode `100644`. 176 of 177 scripts were 755; it was the one exception.

`tests/documentation/phase20.3-contract.sh:11` runs it **directly**, not as `bash <script>`:

```bash
"$ROOT/scripts/docs/validate-public-docs.sh"
```

On Linux that is "permission denied". Git Bash on Windows reports every file as executable, so the local suite passed and the defect was invisible. Fixed with `git update-index --chmod=+x`.

This is the same class of bug as A3's: a check that passes on the machine that wrote it and fails everywhere else. Windows cannot detect it; only a Linux clone can.

## Defect 2: WSL silently uses the Windows toolchain

Three false starts, each worth recording because any contributor working from WSL will hit them:

1. **`bash -s` is not a login shell.** Piping the script over stdin skipped `~/.profile`, so `node` resolved to an old system Node and the suite died with `SyntaxError: Unexpected token '.'` on optional chaining inside `pnpm.cjs`. Use a login shell.
2. **`$VAR` and `$(...)` are expanded before reaching `wsl.exe`.** Inline commands lost their variables, printing `absent: ` with no path and `ls: cannot access ''`. Anything non-trivial has to go in a script file. `/tmp/...` in an argument is also rewritten to the Windows temp directory.
3. **WSL inherits `/mnt/c` on `PATH`.** Both `pnpm` and `corepack` resolved to the Windows fnm multishell:
   ```
   which pnpm: /mnt/c/Users/.../fnm_multishells/11932_.../pnpm
   ```
   A Windows `.cjs` executed by the Linux node across the filesystem boundary. It does not fail cleanly, it just hangs for minutes. Stripping `/mnt/c` from `PATH` and installing pnpm natively took `pnpm install` from stalled to 2m50s.

None of this is a repository defect, but none of it is documented either.

## Follow-up

1. **Add `.gitattributes` with `* text=auto eol=lf`**, and `eol=lf` for `*.sh`. The current LF-clean state depends on every contributor's local `core.autocrlf`; one person with `core.autocrlf=false` on Windows commits CRLF and every shell script breaks on Linux. Cheap insurance for a repository that is 177 shell scripts deep.
2. **Make CI assert the exec bit.** `git ls-files -s '*.sh' | grep -v '^100755'` must be empty. Defect 1 would have been caught by one line, and it will recur every time a script is added from Windows.
3. **Prefer `bash <script>` over direct invocation in tests**, or assert the mode. Direct invocation makes the exec bit a silent dependency.
4. **Document the WSL traps** in the contributor guide: login shell, strip `/mnt/c`, install the pinned pnpm natively. Without this, a WSL contributor's first `pnpm install` appears to hang.
5. Run A4 in CI on `ubuntu-latest` rather than by hand, once the install/build/test steps are added to `.github/workflows/ci.yml`. A manual WSL run proves parity today; CI keeps it.
