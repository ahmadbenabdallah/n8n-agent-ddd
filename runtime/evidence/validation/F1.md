# F1 Build a second domain from the template

Status: PASS (three defects found and fixed)
Date: 2026-09-20
Domain: `domains/demo-booking`

## Command

```bash
cp -r templates/domain-pack domains/demo-booking
# fill the placeholders for a booking business, commerce: none
pnpm validate && pnpm build && pnpm test
```

## Result

| Criterion | Result |
|---|---|
| Second domain passes `pnpm validate` | PASS |
| No `privileged_external_execution` role required with `commerce: none` | PASS, four roles declared, validators accept |
| `validate-platform` and `validate-runtime` resolve the new domain | PASS, no Tunisia id involved |
| Full suite with two domains | 42 passed, 0 failed, 3 skipped |
| Sync plan across both | 2 domains, 31 workflows |
| Registry/directory parity | PASS for both domains |
| Protected-set check | PASS, demo-booking 5 protected, tunisia-dtc 7 |

The domain shares nothing with the reference example:

| | tunisia-dtc | demo-booking |
|---|---|---|
| Business | Direct-to-consumer sales | Appointment booking |
| Workflow ids | `WF-00`…`WF-20` | `BOOK-*` |
| Workflow count | 21 | 10 |
| External system of record | WooCommerce | none |
| Execution role | WF-20 | not required |
| Languages | Arabic, French | English, French |

Four of its ten workflows are adopted from `platform/workflows/library.yaml`
with `from_library`, keeping this domain's own ids. Only two, `BOOK-AVAIL` and
`BOOK-RESERVE`, are business logic. That is the first test of the ADR 0002
claim that a domain writes only its business workflows.

## Defect 1: the test I wrote treats any directory as a workflow

`pnpm test` failed on the first full run:

```
FAIL: demo-booking has workflow directories missing from
      domains/demo-booking/workflows/registry.yaml:
  .impeccable
```

A tool in this environment writes `.impeccable/hook.cache.json` cache
directories. `tests/runtime/workflow-sync.sh` enumerated every directory under
`workflows/`, so a cache directory read as an unregistered workflow. Any
adopter with editor state, `.git` metadata or a tool cache in that folder would
have hit a false failure.

Fixed with `-not -name '.*'`, and `.impeccable/` added to `.gitignore`. Found
only because a second domain was built in a live working tree; the reference
domain had no such directory.

## Defect 2 and 3: the template still named Tunisia's workflow ids

Copying the template carried Tunisia ids into a domain that has none:

| File | Was | Now |
|---|---|---|
| `templates/domain-pack/domain-project.yaml:22` | `authorization_policy: <your-domain-id>-wf10` | `<your-domain-id>-authorization` |
| `templates/domain-pack/knowledge/README.md:3` | "WF-18 ingests them into pgvector" | "The workflow you give the knowledge-ingestion job ingests them" |
| `templates/domain-pack/README.md:9` | "(WF-10 authorization, WF-20 privileged execution, audit, reconciliation)" | the five role names |

The starter an adopter copies told them their domain's authorization policy
was called `<their-domain>-wf10`. The role refactor corrected the specs,
contracts and validators but not the template, because nothing had copied the
template since.

## What this does not prove

The pack is specification-level: catalogs, policies, workflow contracts and
invariants. It has no n8n workflow JSON of its own, and nothing imports the
four adopted library entries into a running n8n, because the import adapter
does not exist. `BOOK-IN` declares a `requires_binding` map naming this
domain's ids, but nothing consumes it yet.

So F1 proves the framework accepts a genuinely different domain. It does not
prove that domain can run.

## Follow-up

1. F3 (what the shared workflows need from a domain) now has a second domain
   to test its parameter list against.
2. The `requires_binding` map is declared but unconsumed. Whatever imports
   library entries into n8n must read it, or adoption stays manual.
3. Consider a test that copies `templates/domain-pack` to a scratch domain and
   runs the validators, so template rot is caught without a human noticing.
   Defects 2 and 3 survived the role refactor precisely because no test ever
   instantiates the template.
