# F4 Ship the agent configuration the architecture claims is a product surface

Status: PASS (two defects found and fixed)
Date: 2026-09-23
Task: NAD-004

## The claim under test

`ARCHITECTURE.md` describes agent configuration as "a product surface for the
next user". F4 predicted that nothing actually shipped on it. That held:
`.claude/agents/` and `.claude/commands/` contained a `.gitkeep` each, and
`.codex/roles/*.toml` were seven name-and-description stubs. An adopter cloning
the repository received no command, no skill and no scaffold.

## What now ships

An installable Claude Code plugin, `plugins/domain-builder/`, listed in the
repository-root marketplace manifest `.claude-plugin/marketplace.json`:

| Surface | File |
|---|---|
| Marketplace | `.claude-plugin/marketplace.json` |
| Plugin manifest | `plugins/domain-builder/.claude-plugin/plugin.json` |
| `/scaffold-domain` | `plugins/domain-builder/commands/scaffold-domain.md` |
| `/adopt-workflow` | `plugins/domain-builder/commands/adopt-workflow.md` |
| `/validate-domain` | `plugins/domain-builder/commands/validate-domain.md` |
| `domain-pack` skill | `plugins/domain-builder/skills/domain-pack/SKILL.md` |
| Scaffold | `plugins/domain-builder/scripts/scaffold-domain.mjs` |

The plugin is for adopters building a domain, not for maintaining this
repository. It references no ai-sdlc configuration, no `.ai-sdlc/` path and no
part of the maintainer workflow; `grep -rn 'ai-sdlc' plugins/ .claude-plugin/`
returns nothing.

The marketplace sources the plugin from the `plugins/domain-builder`
subdirectory of this same repository, so adoption is
`/plugin marketplace add ahmadbenabdallah/n8n-agent-ddd` followed by
`/plugin install domain-builder@n8n-agent-ddd`, with no second repository.

## The scaffold is a script, not a prompt

A command that instructs a model to "copy the template and fill the
placeholders" reproduces exactly the failure F1 documented. So the command runs
`scripts/scaffold-domain.mjs`, which instantiates `templates/domain-pack/` and
fills every platform-contract placeholder: identity, adapters, schema,
versions, policies, the registry, one workflow contract per id, and the
role-to-id mapping.

It names no workflow id of its own. The caller gives a prefix; the platform
roles are mapped onto that prefix. `grep -rnE '\bWF-[0-9]{2}\b' plugins/`
returns nothing, and the scaffold refuses to emit output containing one.

Every placeholder is either substituted or declared in `AUTHOR_FILLS` (the
domain model: entities, aggregates, value objects, commands, events,
projections, business rules, invariant cases). A placeholder in neither is a
hard error that aborts the scaffold before anything is written.

## Defect 1: the template's role lines were unreadable by the platform

`templates/domain-pack/domain.yaml` writes each role with a trailing comment:

```yaml
  authorization: <workflow id>                 # required: the only workflow that may allow an action
```

`scripts/lib/domain-roles.ts` matches `/^\s+([a-z_]+):\s*(\S+)\s*$/`, which
requires the line to end at the id. A pack that kept the template's comment
therefore read as having **no** `workflow_roles` at all, and `pnpm validate`
reported four missing roles against a pack that declared all four. Anyone
copying the template by hand and keeping the explanatory comments would have
hit this and had no way to read the error.

Found because the scaffold reproduced the template faithfully, comments
included. The scaffold now consumes the comment along with the placeholder, and
`tests/platform/domain-scaffold.sh` parses role lines with the platform's own
strict rule so a tolerant test can never pass output the platform rejects.

## Defect 2: the template violated its own protection rule

`templates/domain-pack/workflows/registry.yaml` states, in its own header, that
"every workflow you name in `domain.yaml` `workflow_roles` must be protected",
then marks only the security gate `protected: true`. The four role entries were
unprotected. Fixed in the template; `tests/unit/ownership/protected-workflows.ts`
now reports `4 role workflows all protected` for a freshly scaffolded pack.

## Residual template rot

`templates/domain-pack/domain.yaml` still carried `WF-10, WF-20, WF-16, WF-17
and WF-19` in the comment above `workflow_roles`, and
`business/business-rules.yaml` still gave a "Tunisia example". Both removed:
a scaffolded pack must not carry another domain's ids, not even in a comment.

## What this does not prove

The plugin's install path was exercised against the manifest schema and the
repository layout, not against a live `/plugin marketplace add` from
github.com, which needs the branch merged to `main` first. The scaffolded pack
remains specification-level, like `demo-booking`: no n8n workflow JSON, and
nothing imports the adopted library entries into a running n8n.
